## 1. Связь с BRD (кратко)

- REST + JSON, заголовок `Authorization: <token>`.
- CRUD memes и authorize — по [`brd.md`](brd.md).
- `id` в ответах — **`int`** (в т.ч. после PUT).
- Extra fields в теле BRD не запрещает → не ждать `400` только из‑за лишнего поля.

Базовый URL и учётки задаются окружением (см. [§7](#7-переменные-окружения)).

## 2. Авторизация в тестах

### 2.1. Переиспользование токена

Токены на стенде долгоживущие. Чтобы не плодить их:

1. `GET /authorize/<token>` для `TEST_TOKEN`;
2. если `200` — переиспользовать;
3. иначе — `POST /authorize` с `TEST_USERNAME`.

В проекте: фикстура `auth_token` (`scope=session`).  
Kill-тесты используют **отдельный disposable** токен и не трогают session-токен.

### 2.2. Ожидаемые коды отказа в доступе

| Условие | Ожидаемый статус | Примечание |
|---------|------------------|------------|
| Нет `Authorization` | `401` | строго 401 |
| Невалидный / убитый токен | `401` | строго 401 |
| Валидный токен, но **не владелец** мема (PUT/DELETE) | `403` | observed; в BRD не расписано |
| `GET /authorize/<несуществующий>` | `404` | проверка «жив ли токен» |

### 2.3. Служебный эндпоинт (не в BRD)

| Method / Path | Назначение в тестах |
|---------------|---------------------|
| `GET /authorize/kill/<token>` | инвалидация токена; дальше polling `GET /authorize/<token>` до `404` (tenacity) |

## 3. Уточнения по модели (только для тест-дизайна)

Всё про поля и типы — в [`brd.md` §3](brd.md#3-модель-данных-meme). Для автотестов важно:

| Тема | Правило |
|------|---------|
| Required fields | отсутствие / неверный тип → ожидать `400` (POST/PUT) |
| Extra field | не негатив: API принимает, `200` |
| `id` после PUT | должен быть `int`; иначе BUG-001 |
| PUT-валидация тела | в path/body — **существующий** meme id, иначе часто `404` раньше `400` |

Ответ списка `GET /meme`: массив в корне JSON **или** в ключе `data` (оба варианта допустимы в тестах).

В ответе мема может присутствовать служебное поле вроде `updated_by` — на успешный контракт BRD-полей это не влияет.

## 4. Контракт по эндпоинтам (ожидания автотестов)

Назначение и состав полей — в BRD. Ниже — **позитив / негатив / security** для Pytest.

### 4.1. `POST /authorize`

| Сценарий | Ожидание |
|----------|----------|
| Валидное `name` | `200`, в теле `token` и `user` (== переданному `name`) |
| `name` неверный тип / `null` | `400` |
| Нет поля `name` | `400` |
| Пустая строка `name` | observed: `200`, `user == ""` (зафиксировано тестом) |

### 4.2. `GET /authorize/<token>`

| Сценарий | Ожидание |
|----------|----------|
| Живой токен | `200`, текст содержит `Token is alive` и имя пользователя |
| Неизвестный токен | `404` |

### 4.3. `GET /meme`

| Сценарий | Ожидание |
|----------|----------|
| С валидным токеном | `200`, созданный мем есть в списке, у него есть BRD-поля |
| Без / с неверным токеном | `401` |

### 4.4. `GET /meme/<id>`

| Сценарий | Ожидание |
|----------|----------|
| Существующий id | `200`, поля совпадают с созданными, `id` — `int` и равен запрошенному |
| Несуществующий / невалидный id | `404` |
| Без / с неверным токеном | `401` |

### 4.5. `POST /meme`

| Сценарий | Ожидание |
|----------|----------|
| Валидный payload | `200`, данные в ответе, `id: int`, мем читается через GET |
| Нет required / неверный тип | `400` |
| Extra field | `200` (не ошибка) |
| Без / с неверным токеном | `401` |

### 4.6. `PUT /meme/<id>`

| Сценарий | Ожидание |
|----------|----------|
| Валидное обновление своего мема | `200`, поля как в запросе; `id` в ответе — **`int`** |
| Несуществующий id | `404` |
| Нет required / неверный тип (на существующем id) | `400` |
| Без / с неверным токеном | `401` |
| Другой пользователь (не owner) | `403` |

### 4.7. `DELETE /meme/<id>`

| Сценарий | Ожидание |
|----------|----------|
| Удаление своего мема | `200`; далее GET by id → `404`; мема нет в списке |
| Повторное удаление | `404` |
| Несуществующий / невалидный id | `404` |
| Без / с неверным токеном | `401` |
| Другой пользователь (не owner) | `403`; мем остаётся доступен владельцу |

## 6. Известные дефекты

| ID | Эндпоинт | Ожидание (BRD) | Факт | В тестах |
|----|----------|----------------|------|----------|
| BUG-001 | `PUT /meme/<id>` | `id: int` | `id` как `string` | `test_update_meme_response_id_is_int` — `xfail(strict=True)` |

**Нельзя** маскировать BUG-001 так:

```python
assert str(actual_id) == str(expected_id)
```

Нужно: `isinstance(actual_id, int)` + сравнение значения.

## 8. Рекомендации по тест-дизайну

1. Для PUT-негативов на валидацию тела — только **существующий** meme id (`shared_meme_for_put_negatives` / `meme_fixture`).
2. Не заводить негатив «extra field → 400».
3. Session-токен не убивать; для kill — disposable user/token.
4. После create в фикстурах — teardown `DELETE` (или `skip_cleanup`, если тест удалил сам).
5. `id` проверять строго (`int` + equality), особенно после PUT.
6. Ассерты со статусами — точные (`401` vs `403`), без «или».
7. Сообщения ассертов: expected/got + body (и Allure request/response в `_make_request`).
